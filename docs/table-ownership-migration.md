# 表所有权迁移六步模板

> change `cloud-schema-migration-executor`（design.md D7）。本文件是**模板**，不是某一次迁移的记录。
> 每一次真实的表 / 列所有权迁移 MUST 由自己的 OpenSpec change 引用本文件，并在该 change 的 tasks.md 里
> 逐步登记**实际观察期**与**实际信号值**。只引用不登记 = 没有验收。

## 0. 什么时候需要它

把某张表 / 某几列的**写入所有权**从一处移到另一处时（换存储、换服务、拆域、改数据模型），
六步都要走。判据不是「代码改动大不大」，而是「切换过程中是否存在一个时刻，两个地方都可能写同一份事实」。

只读迁移（换读法、加索引、加缓存）不走本模板。

## 1. 六步表

| 步 | 动作 | 验收信号（MUST 是可观测事实，不是「看起来没问题」） | 回退动作 |
| --- | --- | --- | --- |
| 0 准备 | 一条 `kind=expand` 迁移建新表 / 新列，旧路径**完全不动** | `npm run migrate verify` 报新对象齐备且无多余对象；旧路径全量测试通过 | 一条独立 `kind=contract` 迁移删掉新对象。此时无人写它，零数据损失 |
| 1 双写 | 旧所有者仍是**权威写**；同一请求内追加对新表的写。新表写失败 MUST 计错误数并告警，MUST NOT 静默吞，MUST NOT 因新表失败阻断权威写 | 双写错误计数在观察期内为 0；观察期 ≥ 3 个自然日且覆盖 dev 与 ol 各一个完整业务日 | 关双写开关；新表数据作废（尚无人读它） |
| 2 影子读对账 | 读**仍走旧表**；对账器比对新旧两侧，输出差异条数、差异样例与**已比对行数** | 差异条数为 0 **且**已比对行数覆盖旧表全量（或声明的抽样比例）。观察期同步 ≥ 3 个自然日、覆盖 dev 与 ol 各一个完整业务日 | 修双写 → 清空新表 → **重新计观察期**（不是接着上次的天数往下数） |
| 3 切读 | 读切到新表，旧表**继续双写** | 切读前后的业务行数、错误率与既有日志关键字计数一致；开关可秒切回 | 开关切回读旧表。无任何数据动作 |
| 4 停旧写 | 新所有者成为唯一写入者，旧表停写 | 观察期内 `pg_stat_user_tables` 上旧表的 `n_tup_ins / n_tup_upd / n_tup_del` **不再增长** | 恢复旧写开关（恢复的是**双写**，不是把旧表重新当权威读） |
| 5 收缩 | 一次**独立 change** 的 `kind=contract` 迁移删旧表 / 旧列 | contract 单独部署、单独验证；账本记 `kind=contract`、`applied_by` 含授权者 | **不可逆。回退只能从步 5 之前的备份恢复。** |

## 2. 每一步的硬要求

### 步 1 双写：失败必须留下痕迹

- 新表写失败 MUST **计错误数并告警**。
- MUST NOT 静默吞（`catch {}` / 只 `console.debug`）。一次被吞掉的双写失败会让步 2 的对账看起来「只差几行」，
  而真实原因是某一类请求从来没写进新表 —— 这类缺口在切读之后才暴露，那时旧表已经停写。
- MUST NOT 因新表写失败**阻断权威写**。新表此刻还没有任何读者，为它牺牲可用性是纯亏。

### 步 2 影子读对账：覆盖率为 0 时结论是「未验证」

- 对账器 MUST 同时上报**差异条数**与**已比对行数**。
- 已比对行数为 0 时，结论 MUST 是「未验证」，MUST NOT 报「一致」或「通过」。
  「没发现差异」和「比对过且没有差异」是两件事；把前者当后者，就是用一次「假设」冒充一次「验证」。
- 抽样对账 MUST 写明抽样比例与抽样口径，MUST NOT 只报「抽查了一些」。

### 步 4 停旧写：以实际写入量为准

- 验收依据 MUST 是旧对象在观察期内的**实际写入统计**（`pg_stat_user_tables`）不再增长。
- MUST NOT 用「代码里已经删掉调用」当验收。删掉的是**已知**调用点；还有定时任务、恢复路径、
  运维脚本和另一个 target 上跑着的旧构建。

### 步 5 收缩：诚实标注不可逆

- 本步**不可逆**。回退方式 MUST 记为「从备份恢复」。
- 文档与 change 说明 MUST NOT 把这一步描述为「可回滚」。
- 因此步 5 MUST 在观察期结束、备份存在**且校验过**之后执行。「备份应该有」不是「备份存在且校验过」。
- 共库期收缩需要执行器的显式授权：`npm run migrate up --allow-contract --by=<操作者>`，授权者入账本。

## 3. 观察期口径

- 步 1 与步 2 **各** ≥ 3 个自然日。
- 每一步的观察期 MUST 覆盖 **dev 与 ol 各一个完整业务日**（不是「跑满 72 小时」——周末的 72 小时证明不了工作日的负载形态）。
- 每次实际表迁移的 change MUST 在自己的 tasks.md 登记：起止日期、覆盖了哪几个业务日、每步的实际信号值。
- 观察期因为修复而重置的，MUST 记为重置并重新计天，MUST NOT 接着上次的天数往下数。

## 4. 跨服务场景

步 1 的双写若落在**两个进程**里（旧所有者在 A、新所有者在 B）：

- MUST 走**持久命令 / Outbox**：A 在自己的事务里写一条待投递记录，B 消费并写新表，消费带幂等键。
- MUST NOT 依赖 `pg_advisory_lock` 表达跨进程互斥。advisory lock 是**数据库级**作用域：
  拆 schema 仍互斥，**拆库即静默失去互斥** —— 两侧各自加锁都会成功、不报任何错。
- MUST NOT 依赖跨进程共享事务。两个进程之间没有共享事务，只有「看起来像事务」的假象。
- 现成先例：`src/publish-agent/publish-approval-outlet.ts` 的授权 Outbox、
  `src/risk/risk-counter-outbox-store.ts` 的风控记账 Outbox。

## 5. 与迁移执行器的接口

- 步 0 的 expand 迁移与步 5 的 contract 迁移 MUST 是**两个文件、两个 change、两次部署**。
- 两者都 MUST 带 `-- aidcp:kind=` 与 `-- aidcp:objects=` 头声明（规则见 `migrations/README.md`）。
- 步 0 与步 5 之后各跑一次 `npm run migrate verify`，把缺失清单与多余清单原文记进 change 的 tasks.md。
- 收缩 MUST NOT 与任何 expand 迁移同批交付：同批交付会让「回滚这次部署」同时回滚掉一个不可逆动作，
  而不可逆动作是回滚不掉的。
